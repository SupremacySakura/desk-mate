# 双端界面实现验收

- macOS：客户端已构建，主窗口已在本机打开。用原生视图生成扩展显示与设置预览，使用示例显示器状态，不是 USB 联调截图。主机合约测试通过。
- 鸿蒙：新版调试 HAP 已用原有华为开发者配置签名，经 `hdc` 覆盖安装并成功启动。真机截图确认连接首页正常显示；签名在临时工程副本中完成，未改仓库签名配置。
- 真机联调：Mac 识别到可用扩展显示器并打开了正式客户端。本轮启动后，平板仍在 `hdc` 模式，尚未建立 USB 配件会话；未启用前台保活脚本。
- 后续真机复测：重开两端应用后，Mac 识别到 USB 配件，用户确认平板显示了扩展桌面，无新的授权弹窗。自动重连和拔插恢复仍未验收。
- 性能初测：两次会话的 Mac 编码均值分别为 10.28 和 9.61 帧/秒，编码器均报告丢弃 0 帧。测试未控制画面活动，不能据此判断动态帧率或平板实际显示帧率。最新会话采集随后停止，未能完成动态对照；Mac 界面主线程采样也未成功。
- 性能复测：Mac 编码会话持续 83.744 秒，输出 4,566 帧（平均 54.52 帧/秒），编码器报告丢弃 0 帧。该统计覆盖整个会话，不是指定 15 秒的窗口；未取得平板渲染计数或 Mac 卡顿时的有效主线程样本。采集停止后客户端进程仍在。
- 后续诊断：用户观察到平板帧率在 0 和 4 之间跳动；该读数按约 250 毫秒内成功提交到 Surface 的帧数折算，不是面板刷新率。Mac 同一进程累计提交 4,565 帧，协议发送队列接受 849 帧，拒绝 3,716 帧，桥接入口积压丢弃 0 帧。接受入队不等于成功写入 USB；这些是累计计数，不能与平板瞬时读数直接对齐。读取时连接已失败（5 次握手后 `hello_timeout`），无法采集同一动态窗口的双端计数。
- 恢复原因复测：新版通过录屏权限预检并建立 USB 串流。会话中最早记录的恢复由 Mac 队列帧龄超限触发（20.78 毫秒，阈值 18 毫秒）；约 271 毫秒后收到首次平板关键帧请求。之后 17.07 秒的帧计数区间内提交 920 帧、入队 164 帧、等待关键帧拒绝 756 帧，USB 写入超时增加 157 次。同一次约 18 秒的探针采样记录到 20 次帧龄超限、88 条平板请求（含重试）、0 次队列字节超限。平板解码输出和 Mac 主线程尚无同窗样本；上述时间顺序不足以证明 USB 超时或平板请求的具体因果关系。
- 帧龄阈值对照：实验版通过录屏预检并确认 `frame_age_limit_ns=60000000`，保持 HEVC 2800×1840@60 与原 USB 设置。17.115 秒内提交 776 帧、入队 262 帧、因等待关键帧拒绝 513 帧，USB 写入超时增加 147 次；同期探针记录到帧龄超限 9 次、队列字节超限 3 次、平板请求 82 条（含重试）。相比上一轮 18 毫秒组，Mac 入队速率从 9.6 升至 15.3 帧/秒，关键帧等待拒绝占比从 82.2% 降至 66.1%，但平均提交负载也从 53.9 降至 45.3 帧/秒。60 毫秒组末 8.064 秒提交约 55.2 帧/秒、入队约 13.9 帧/秒、关键帧等待拒绝约 75.1%。这不是同一构建下的重复对照，尚未取得平板的同步输出计数，也未测量延迟变化，不据此更改默认阈值。
- 平板侧反馈与 USB 断链：60 毫秒组的平板读数仍在 0 和 4 帧/秒间跳动。连接诊断页只有累计输出帧数，串流期间 `hdc` 无目标，未能取得对应的接收和解码计数。实验组在 `20:54:09.145` 的累计采样首次记录超时已写入 7,168 字节，随后 `20:54:11.632` 报 `heartbeat_timeout`；低帧率早于该事件，时间顺序也不足以断定断链原因。Mac USB 写入适配器原先对该部分进度返回零，重试会从原偏移重发。修复后使用实际进度推进偏移，仅重试未写出的部分；模拟部分超时的回归测试修复前失败、修复后通过。尚未安装修复版或复测真机。
- 平板日志归档复查：拔插后恢复 `hdc`，从 `deskmate.461.20261124-204322.gz` 读取到 60 毫秒组的 `DeskMateEngine` 记录。平板时间戳 `20:53:40.843` 至 `20:53:47.883` 的 7.040 秒内，`rx` 从 2433 增至 2447，解码提交和 Surface 输出均从 211 增至 225（约 2.0 帧/秒），解码丢帧、输出错误与 USB 读错误计数未增加。相邻 Mac 采样点 `20:53:40.972` 至 `20:53:48.034` 的 7.062 秒内，提交从 618 增至 1006，入队从 307 增至 403（约 13.6 帧/秒）。按两端墙上时钟近似对照，未做时钟校准；`rx` 是协议交付给平板引擎的完整帧，并非 USB 上所有到达的帧或字节。证据将这一时段的主要差距缩小到 Mac 入队之后、平板解码提交之前，尚不能区分调度器淘汰、USB 送达与平板协议恢复过滤各自的占比。
- 共享核心：协议、会话和调度测试通过。
- 代码修复：Host 合并同一编号、仍在等待或发送中的平板关键帧请求，发送完成后仍接受重试；回归测试验证了后续预测帧不会因发送中的重复请求被拒绝。Mac 将关键帧请求轮询从 250 毫秒的界面刷新中拆出，以约 33 毫秒间隔读取桥接状态；界面刷新与输入轮询遇到 USB 会话锁忙时跳过本轮。已构建 Mac 应用，Mac 合约、部分写入回归和共享核心测试通过。没有变更默认帧龄阈值，没有替换已安装版本；平板实际帧率、Mac 界面流畅度和断链改善仍待真机复测。
- 首帧信号：当前使用解码器成功输出到 Surface 的计数，不是面板呈现回执。该行为和帧率读数仍需实机核对。
- 修复版真机复测：Mac 包备份后替换安装，录屏预检通过，平板端未重装。以 HEVC 2800×1840@60、18 毫秒默认阈值建立串流。Mac 采样 `21:05:23.568` 至 `21:05:41.799` 共 18.231 秒，提交 1053 帧（57.8 帧/秒）、入队 486 帧（26.7 帧/秒）、因等待关键帧拒绝 568 帧（53.9%），USB 写入超时增加 241 次，超时已写字节增加 11264，`bulkErrors` 未增加。与历史 18 毫秒组相比，入队 9.6→26.7 帧/秒，关键帧等待拒绝占比 82.2%→53.9%；两轮负载接近但不是严格控制实验。从 `21:05:16.470` 到 `21:06:01.591` 持续报告串流，未见该段断链。AOA 串流中 `hdc` 不可用，没有取得平板同期输出计数，也尚未确认 Mac 界面体感。

- 平板真机反馈：修复版复测时，用户观察到平板帧率浮层显示 8–12 帧/秒，高于旧版的 0–4 帧/秒。这是界面按短窗口计算的 Surface 输出速率，不是面板刷新的测量值，也不是完整采样窗的平均值。确认低帧率有所改善，仍未达到流畅水平。

## 待真机验证

1. 准备可用的扩展显示器，在平板上安装签名 HAP。从 Finder 和平板桌面打开应用，插线并授权，不运行前台保活脚本。若 AOA 切换时应用退回后台，从平板桌面重新打开；仍不能出画则记录为未通过。
2. 确认平板不在握手阶段进全屏，首帧后进入全屏；返回首页、进入设置及返回画面不销毁解码 Surface，同一连接不会再次自动跳转。
3. 拒绝授权应回到带重试入口的页面，不重复弹窗；拔线后确认自动回到等待状态并可重新接线。
4. 在 Mac 屏幕录制和辅助功能权限分别关闭的情况下检查提示与降级；确认已授权时的帧率显示和反向触控。
